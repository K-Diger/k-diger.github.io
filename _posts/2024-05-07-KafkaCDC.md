## 배경

DB의 변경을 다른 시스템에 전달해야 했다. 처음 떠오른 방법은 **애플리케이션이 저장할 때 이벤트도 함께 발행하는 것**이었다.

그런데 이 방식에는 앞서 [FCM을 붙이면서 겪은 문제](/posts/FCM/)와 같은 구멍이 있다. 저장과 발행이 다른 시스템에 대한 두 개의 쓰기라서, **하나가 성공하고 하나가 실패할 수 있다.**

CDC는 이 문제를 다른 자리에서 푼다. **애플리케이션이 아니라 DB가 이미 남기고 있는 변경 기록을 읽는다.**

정리하면서 확인하고 싶었던 것들이다.

- CDC가 읽는다는 "변경 기록"이 정확히 무엇인가?
- 애플리케이션에서 이벤트를 발행하는 것과 무엇이 다른가?
- 커넥터가 죽었다 살아나면 어디서부터 다시 읽는가?
- 도입하면 무엇을 감수해야 하는가?

---

구축할 환경은 각기 다른 온프레미스 서버 인스턴스에 Kafka를 KRaft 모드로 띄우고 그 위에 CDC를 올리는 것이다.

따라서 각 노드에는 `Controller`, `Broker`, `Connect` 총 3개의 프로세스가 동작한다. KRaft 모드 자체는 [따로 정리한 글](/posts/KRaft/)에 있다.

# Step 1. MSSQL 접속 및 데이터베이스, 스키마, 테이블 생성

1. `SOURCE`, `EXTERNAL` 데이터베이스를 생성
2. `SOURCE`, `SOURCE` 데이터베이스 내에 `dbo` 스키마를 사용
3. `SOURCE`, `SOURCE` 데이터베이스 내에 `dbo` 스키마 내에 `MEMBER_BASE` 테이블 생성

```sql
-- SOURCE 라는 데이터베이스를 사용
USE [EXTERNAL];

create table dbo.MEMBER_BASE(
    member_id bigint primary key,
    nickname nvarchar(50)
)

USE SOURCE;

create table dbo.MEMBER_BASE(
    member_id bigint primary key,
    nickname nvarchar(50)
)

EXEC sys.sp_cdc_enable_db;

ALTER DATABASE SOURCE SET CHANGE_TRACKING = ON(CHANGE_RETENTION = 3 DAYS, AUTO_CLEANUP = ON)

EXEC sys.sp_cdc_enable_table
      @source_schema = 'dbo',
      @source_name = 'MEMBER_BASE',
      @role_name = 'sa';
```

```text
        // 설명: 단일 폴링 작업에서 가져올 최대 레코드 수
        "max.poll.records": "500"
    }
}
```

# 이론으로

[로그 기반 CDC 5가지 장점](https://debezium.io/blog/2018/07/19/advantages-of-log-based-change-data-capture/)

Debezium을 사용하는 Source CDC는 로그 기반으로 동작하게된다.

즉, DBMS의 binlog를 활용하여 변경된 데이터를 감지하게 되는 것인데 이 방식의 구체적인 내용과 장점을 살펴본다.

## Binary Log

[MySQL 공식문서 - BinaryLog](https://dev.mysql.com/doc/refman/8.4/en/binary-log.html)

Binary Log는 데이터베이스의 변경 사항을 기록하는 기능이다. 주로 소스 서버의 변경 사항을 레플리카 서버로 전송하는 데이터`복제`나 백업 이후의 변경 사항을 재실행하여 최신 상태로 `복구`할 때 활용된다.

바이너리 로그는 예상치 못한 중단이 일어날 때를 대비하여 완전히 완료된 트랜잭션만 기록하고 다시 읽는 방식으로 동작한다.

즉, 트랜잭션이 끝나지 않은 내용은 이후 BinaryLog에 기록되지 않아 DB에 적용되지 않는다.

참고로, `Debezium`을 MySQL 사용하기 위해 Binary Log를 활용한다는 내용이었지만 `MSSQL`, `PostgreSQL`등 각자만의 Binary Log의 역할을 하는 개념을 도입시키거나 DBMS단위에서 자체적인 CDC를 제공한다.

---

## Global Transaction ID - GTID

[MySQL 공식문서 - Replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html)

MySQL에서는 Binary Log방식이 아닌 Transaction ID를 통해 복제를 수행하는 GTID방식도 존재한다.

## 정리하며

처음 던진 질문들에 대한 답이다.

**변경 기록이 무엇인가.** DB가 복제를 위해 이미 남기고 있는 로그다. MySQL이면 바이너리 로그, SQL Server면 CDC 테이블이다. **원래 목적은 복제본을 만드는 것**이고, CDC 도구는 자기를 복제본인 척하고 그 로그를 읽는다.

그래서 **DB 입장에서는 특별한 부담이 아니다.** 어차피 남기고 있던 것을 하나 더 읽어갈 뿐이다. 애플리케이션 테이블에 트리거를 걸거나 주기적으로 조회하는 방식과 여기서 갈린다.

**애플리케이션 발행과 무엇이 다른가.** 원자성이다. 애플리케이션이 저장하고 나서 이벤트를 발행하면 그 사이에 죽을 수 있고, 그러면 데이터는 바뀌었는데 아무도 모른다. **CDC는 커밋된 것만 로그에 남으므로 그 틈이 없다.**

대신 **애플리케이션의 의도가 사라진다.** 로그에 남는 것은 "주문 테이블의 이 행이 이렇게 바뀌었다"이지 "주문이 취소됐다"가 아니다. 받는 쪽이 컬럼 변화를 보고 의미를 되짚어야 한다.

**의미가 중요하면 아웃박스 패턴이 낫다.** 이벤트를 같은 DB의 테이블에 함께 저장하면 원자성도 지키고 의미도 담을 수 있다. 그리고 그 테이블을 CDC로 읽으면 된다.

**커넥터가 죽으면 어디서부터 다시 읽는가.** 오프셋을 Kafka 토픽에 저장해두고 거기서부터 이어간다. 그래서 **재시작해도 처음부터 다시 읽지 않는다.**

여기에 조건이 있다. **DB가 그 시점의 로그를 아직 갖고 있어야 한다.** 바이너리 로그의 보관 기간이 지나면 그 구간이 사라지고, 그러면 전체를 다시 읽는 스냅샷부터 시작해야 한다. 커넥터가 오래 멈춰 있으면 이 상황이 온다.

**감수할 것.** 세 가지가 눈에 띄었다.

**중복이 올 수 있다.** 오프셋을 저장하기 직전에 죽으면 같은 변경이 두 번 발행된다. 받는 쪽이 여러 번 처리해도 결과가 같도록 만들어야 한다.

**스키마 변경이 그대로 전파된다.** 컬럼을 추가하거나 이름을 바꾸면 메시지 형태가 바뀐다. 스키마 레지스트리를 두거나 호환되는 방식으로만 바꾸는 규칙이 필요하다.

**운영 대상이 늘어난다.** Kafka Connect 클러스터가 하나 더 생기고, 커넥터마다 상태를 봐야 한다. 커넥터가 조용히 멈춰 있으면 데이터가 안 오는데 아무도 에러를 안 본다. **지연 시간을 지표로 뽑아 감시하는 것이 필수**였다.

구축하고 나서 남은 감각은 **CDC가 "이벤트를 만드는 도구"가 아니라 "이미 있는 것을 옮기는 도구"** 라는 것이었다. 그래서 안전하지만, 그만큼 의미를 담을 자리가 없다. 무엇을 전달하고 싶은가에 따라 이 방식이 맞을 수도 아닐 수도 있었다.
